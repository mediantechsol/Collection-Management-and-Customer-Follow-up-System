# دليل التشغيل والترحيل

من مشروع Supabase فارغ إلى نظام يعمل ببيانات العميل الحقيقية.

---

## 1) قاعدة البيانات

مساران — اختر واحداً.

### أ) بلا تثبيت أي شيء: لوحة التحكم

مفاتيح الواجهة (`VITE_*`) **لا تصلح للترحيل**؛ هي تتحدث مع PostgREST ولا تستطيع
إنشاء جداول أو سياسات. أبسط طريق بلا رمز وصول ولا كلمة مرور قاعدة بيانات:

1. `SQL Editor` → `New query` → الصق **`supabase/migrate_all.sql`** كاملاً → Run.
2. الصق `supabase/seed.sql` وشغّله.
3. `Database → Extensions` → فعّل **pg_cron**، ثم شغّل
   `supabase/migrations/20260101000005_cron.sql` وحده.

> `migrate_all.sql` مولَّد آلياً من `migrations/` عبر `bash supabase/build_migrate_all.sh`.
> ملف pg_cron مستثنى منه عمداً: محرر SQL ينفّذ اللصقة كمعاملة واحدة، فلو لم تكن
> الإضافة مفعّلة لتراجع الترحيل كله بسببها.

### ب) عبر Supabase CLI

```bash
npm i -g supabase
supabase login                                     # رمز وصول عبر المتصفح
supabase link --project-ref <معرّف-المشروع>        # يطلب كلمة مرور قاعدة البيانات
supabase db push                                   # يشغّل supabase/migrations بالترتيب
supabase db execute --file supabase/seed.sql       # فئات افتراضية + الإعدادات
```

هذا المسار مطلوب على أي حال لنشر Edge Function وتوليد الأنواع لاحقاً.

الترحيلات بالترتيب:

| الملف | المحتوى |
|---|---|
| `20260101000000_schema.sql` | الجداول والدوال والـ views |
| `20260101000001_auth.sql` | ربط `auth.users` + دوال الصلاحيات + `user_directory` |
| `20260101000002_rls.sql` | سياسات RLS |
| `20260101000003_audit.sql` | triggers سجل التدقيق |
| `20260101000004_rpc.sql` | التنبيهات، الاستيراد، رفع الحالة |
| `20260101000005_cron.sql` | جدولة التنبيهات اليومية |

> **pg_cron**: إن لم يكن مفعّلاً سيفشل الملف الأخير. فعّله من
> Database → Extensions → `pg_cron` ثم أعد `db push`. بدونه يبقى النظام يعمل،
> لكن التنبيهات لن تُولَّد إلا بالزر اليدوي.

## 2) Edge Function

```bash
supabase functions deploy admin-users
supabase secrets set INTERNAL_EMAIL_DOMAIN=dr-ayman.local
```

يجب أن تطابق القيمة `VITE_INTERNAL_EMAIL_DOMAIN` في الواجهة و`internal_email_domain`
في جدول `settings`، وإلا فشل تسجيل الدخول: الحساب يُنشأ بنطاق والدخول يبحث بنطاق آخر.

## 3) الواجهة

```bash
cd app
cp .env.example .env.local     # املأ URL و anon key من Project Settings → API
npm install
npm run dev                    # http://localhost:5173
```

⚠️ **المفتاح المطلوب هو العلني وحده**: `sb_publishable_…` (أو `anon` في المشاريع
الأقدم). أي متغيّر باسم `VITE_*` يُحزَم حرفياً في ملف JavaScript يُرسل لكل متصفح.

وضع المفتاح السري (`sb_secret_…` / `service_role`) هناك يعني أن كل زائر يحمل
مفتاحاً **يتجاوز كل سياسات RLS** — أي أن نموذج الصلاحيات كله يصبح بلا أثر، ويستطيع
أي مستخدم قراءة وتعديل وحذف كامل قاعدة البيانات من أدوات المطوّر.

المفتاح السري له مكان واحد في هذا المشروع:

```bash
supabase secrets set SUPABASE_SERVICE_ROLE_KEY=...   # Edge Function فقط
```

إن سبق أن وُضع في `.env.local`، استبدله بالعلني ثم اضغط **Rotate** عليه من لوحة
التحكم احتياطاً.

## 4) أول مدير نظام

مشكلة البيضة والدجاجة: إنشاء المستخدمين يتطلب مديراً، ولا يوجد مدير بعد.
يُحلّ مرة واحدة يدوياً:

1. **Authentication → Users → Add User**
   - البريد: `ayman@dr-ayman.local` (نفس النطاق أعلاه)
   - كلمة مرور قوية، وفعّل **Auto Confirm User**.
2. من SQL Editor:

```sql
update public.users set
  full_name       = 'د. أيمن نجيب',
  username        = 'ayman',
  role_id         = (select id from public.roles where name_role = 'مدير النظام'),
  status          = 'نشط',
  allowed_screens = array['dashboard','followups','customers','notifications',
                          'collections','import','performance','users']
where id = '<UUID الحساب من الخطوة 1>';
```

بعدها يُنشأ باقي المستخدمين من داخل التطبيق (شاشة المستخدمون) — لا حاجة لأي SQL.

> كل حساب جديد يبدأ **موقوفاً** بلا شاشات. اضبط صلاحياته أولاً ثم اضغط «تنشيط».
> اكتب **الاسم الكامل مطابقاً لاسم المسؤول في ملف Excel** (ايمن، ابوبكر، بلال، عمر،
> مكاتب) ليُربط عملاؤه تلقائياً عند الاستيراد.

## 5) ترحيل بيانات العميل

الترتيب مهم:

### أ) المستخدمون أولاً
أنشئ حسابات مسؤولي التحصيل الخمسة قبل أي استيراد، وإلا استُورد العملاء بلا مسؤول
وستحتاج إعادة الاستيراد لربطهم.

### ب) بيانات العملاء وتواريخ الاستحقاق
شاشة **استيراد Excel** ← تبويب «استيراد بيانات العملاء والاستحقاق» ← ارفع
`متابعه العملاء.xlsm`.

المعاينة تعرض أسماء المسؤولين في الملف: الأخضر مطابق لمستخدم موجود، والأصفر لا.
عالج الأصفر قبل التأكيد.

### ج) الأرصدة — أهم خطوة
شاشة الاستيراد ← تبويب «استيراد الأرصدة» ← ارفع `ارصدة العملاء ايمن.xlsx`.

> **في أول استيراد فقط: أزل علامة «اشتقاق الدفعات المحصّلة».**
> ملف الأرصدة يحمل أرصدة دائنة تاريخية متراكمة من سنوات. مع تفعيل الخيار سيعتبرها
> النظام تحصيلاً حدث اليوم، فتظهر مئات الدفعات الوهمية وحوافز غير مستحقة.
> في كل استيراد **بعد** الأول، أبقِ الخيار مفعّلاً — عندها يقارن بالاستيراد السابق
> فيلتقط التحصيل الفعلي فقط.

### د) التحقق من الترحيل
قارن إجمالي المستحق في لوحة المدير بعمود «اجمالي المبلغ المستحق بالريال» في شيت
المتابعة. الفرق المتوقع الوحيد سببه سعر الصرف: الشيت يستخدم 535/140 لكل صف بينما
النظام يستخدم القيمة المركزية في `settings` (530/141 افتراضياً). وحّدهما قبل المقارنة.

## 6) اختبارات القبول

**لا تسلّم النظام للاستخدام الفعلي قبل نجاحها كلها.**

```bash
cd app && npm test && npm run typecheck
```

ثم من SQL Editor شغّل `supabase/tests/rls_checks.sql` بعد وضع معرّفات المستخدمين
في أعلاه. يجب أن تظهر كل الأسطر ✔ بلا استثناء. السكربت داخل معاملة تنتهي بـ
`rollback` فلا يترك أثراً.

ثم تحقق يدوياً:

- [ ] تسجيل دخول حقيقي بكل دور من الأدوار الأربعة.
- [ ] مسؤول التحصيل لا يرى في شاشة العملاء إلا عملاءه، ضمن فئاته.
- [ ] المستخدم الموقوف لا يستطيع الدخول إطلاقاً.
- [ ] استيراد ملف الأرصدة مرتين متتاليتين لا يغيّر إجمالي المديونية.
- [ ] اعتماد دفعة محصّلة يُظهر حافزاً في شاشة الأداء، وإلغاء الاعتماد يزيله.
- [ ] رفع حالة عميل للمدير من حساب مسؤول تحصيل ينجح ويظهر عند المدير.
- [ ] فتح النظام من متصفح جوال: القوائم والجداول مقروءة.

## 7) النشر

```bash
cd app && npm run build      # المخرجات في app/dist
```

انشر `app/dist` على Vercel أو Netlify أو أي استضافة ملفات ثابتة، مع ضبط
`VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY` في متغيّرات البيئة هناك.

من إعدادات Supabase → Authentication → URL Configuration، أضف نطاق الموقع المنشور.

## 8) الصيانة الدورية

| المهمة | الوتيرة |
|---|---|
| استيراد ملف الأرصدة المحدَّث | حسب دورة المحاسبة (أسبوعياً/شهرياً) |
| اعتماد الدفعات المشتقّة من شاشة الدفعات | بعد كل استيراد |
| مراجعة أسعار الصرف في الإعدادات | عند تغيّر السوق |
| مراجعة `cron.job_run_details` للتأكد من عمل التنبيهات | شهرياً |

```sql
-- التأكد من عمل الجدولة اليومية
select * from cron.job_run_details order by start_time desc limit 10;
```

## 9) بعد ربط المشروع

بدّل الأنواع المكتوبة يدوياً بأخرى مولَّدة من المخطط الفعلي:

```bash
cd app && npm run gen:types     # ينتج src/types/database.ts
```

ثم استبدل استخدامات `src/types/models.ts` تدريجياً بها.
