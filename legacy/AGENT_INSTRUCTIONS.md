# تعليمات الوكيل (AGENT_INSTRUCTIONS)

قواعد تشغيلية لأي أداة/وكيل ذكاء اصطناعي يكمل تطوير هذا المشروع. اقرأها قبل كتابة أي سطر كود، والتزم بها طوال الجلسة.

## 1. اقرأ أولاً، لا تخمّن

قبل أي تعديل: افتح `PROMPT.md` كاملاً، ثم `frontend/collection-system.html`، ثم ملفات `database/*.sql` بالترتيب. لا تفترض بنية بيانات أو قاعدة عمل غير موجودة صراحة بهذه الملفات — إن احتجت قراراً غير محسوم، ارجع لقسم "قرارات عمل معلّقة" بـ `PROMPT.md` واسأل المستخدم بدل الافتراض.

## 2. أسلوب الكود المتّبع حالياً — حافظ عليه

- **JavaScript صافٍ (Vanilla)** بدون أي إطار عمل (لا React/Vue بالواجهة الحالية). لو قرّرت الانتقال لإطار عمل، هذا قرار معماري كبير يجب طرحه على المستخدم صراحة قبل التنفيذ، وليس افتراضاً ضمنياً.
- كل دالة عرض (render) تبني `innerHTML` كسلسلة نصية ثم تُعلّق مستمعي الأحداث (event listeners) بعدها مباشرة. حافظ على هذا النمط عند إضافة شاشات جديدة، أو وثّق سبب تغييره.
- **دائماً** مرّر أي نص قادم من المستخدم عبر دالة `esc()` قبل إدراجه بـ `innerHTML` — هذا هو الدفاع الوحيد الموجود ضد XSS بالكود الحالي. أي إضافة تتجاوز هذا تُعتبر ثغرة أمنية.
- الألوان والمسافات كلها عبر CSS Variables في `:root`. لا تُدخل قيم Hex مباشرة بمكان جديد — أضفها كمتغيّر جديد إن احتجت لونًا لا يوجد.
- التسميات كلها بالعربية بالواجهة، لكن أسماء المتغيرات/الدوال بالكود إنجليزية. حافظ على هذا الفصل.

## 3. الأمان — لا تساوم على هذه النقاط

- **لا تُعد أبداً** حقل `password` كنص صريح بأي جدول أو حالة تطبيق. المصادقة حصراً عبر Supabase Auth (`auth.users`)، والتفاصيل بـ `database/01_link_auth.sql`.
- أي منطق صلاحيات يُضاف بالواجهة (JS) **يجب أن يكون له مقابل بسياسات RLS** بقاعدة البيانات أيضاً. لا تكتفِ بإخفاء زر أو شاشة بالواجهة فقط — هذا قابل للتجاوز بسهولة من أي مستخدم متمرس بأدوات المطوّر. راجع `database/02_rls_policies.sql` كمرجع للنمط المتّبع.
- لا تُخزّن مفاتيح Supabase (service_role key خصوصاً) بكود الواجهة (client-side) إطلاقاً — فقط `anon key` مسموح بها بالمتصفح. أي عملية تحتاج صلاحيات مرتفعة (مثل إنشاء مستخدم جديد) تمر عبر خادم/Edge Function.

## 4. قبل الادّعاء بأن شيئاً "جاهز للإنتاج"

لا تصف أي تسليم بأنه "Production Ready" ما لم يحقق كل التالي فعلياً (وليس نظرياً):
- [ ] مصادقة حقيقية مختبرة (تسجيل دخول/خروج فعلي عبر Supabase Auth، وليس بيانات وهمية).
- [ ] RLS مفعّلة ومُختبرة بكل الأدوار الأربعة (جرّب فعلياً: هل مسؤول تحصيل يرى عملاء غير معيّن عليهم؟ يجب ألا يرى).
- [ ] لا توجد أي بيانات حساسة (كلمات مرور، مفاتيح API) بكود الواجهة أو بأي ملف يُرفع لمستودع عام.
- [ ] القرارات المعلّقة بـ `PROMPT.md` (قسم 6) محسومة فعلياً مع صاحب المشروع، وليست افتراضات من عندك.
- إن لم يتحقق أحد هذه الشروط، صرّح بذلك للمستخدم بوضوح بدل وصف العمل بأنه مكتمل.

## 5. عند إضافة جدول أو حقل جديد بقاعدة البيانات

1. أضف عمود/جدول بملف SQL جديد مرقّم (`04_...sql` وهكذا) — لا تُعدّل الملفات الرقمية القديمة (00-03) إن كانت قد نُفِّذت فعلاً على بيئة حقيقية، لتجنّب كسر الترحيل (migration) لمن نفّذها سابقاً.
2. أضف سياسة RLS مطابقة بنفس الملف الجديد أو بملف مرافق له.
3. حدّث `PROMPT.md` (قسم "قاموس البيانات") بنفس الرسالة/الجلسة — لا تترك التوثيق يتأخر عن الكود.

## 6. الاختبار

لا يوجد حالياً ملف اختبارات آلية مرفق بهذه الحزمة (رغم أن تعليقات بالكود الأصلي تشير لملف `test_logic.js` بـ 22 اختباراً — لم يُرفَق ضمن الملفات المستلمة). قبل أي تعديل على دوال منطق العمل الصافية بأعلى `<script>` (حساب التاريخ، العملة، الحافز)، اكتب اختباراً يدوياً بسيطاً (حتى `console.assert` كافٍ) يغطي الحالة قبل وبعد التعديل — هذه الدوال تُستخدم بأكثر من شاشة، وأي كسر بها يؤثر على النظام كاملاً.
