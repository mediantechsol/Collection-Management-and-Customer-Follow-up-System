# برومنت المشروع — نظام إدارة التحصيل ومتابعة العملاء

انسخ هذا الملف كاملاً كأول رسالة لأي أداة ذكاء اصطناعي أخرى (أو مطوّر بشري) لإكمال العمل على المشروع بدون فقدان أي سياق.

---

## 1. السياق العام

نظام لإدارة التحصيل ومتابعة العملاء لصالح "مكتب الدكتور أيمن لخدمات الدواجن". يستخدمه ثلاثة أنواع مستخدمين رئيسيين (+ دور رابع مخصص قابل للتوسع):

- **مدير النظام** — صلاحية كاملة على كل الشاشات والبيانات.
- **المحاسب** — يدير العملاء والأرصدة والاستيراد، دون إدارة مستخدمين.
- **مسؤول التحصيل** — يرى فقط عملاءه المُعيَّن عليهم، ضمن فئات عملاء محددة له، ويتابعهم (اتصال/واتساب/زيارة) ويسجّل نتائج التواصل.
- **مستخدم مخصص** — دور بدون صلاحيات افتراضية، يُبنى بالكامل من صلاحيات مخصّصة لكل مستخدم (شاشات + فئات + إجراءات + حقول ظاهرة).

الواجهة عربية بالكامل، اتجاه RTL.

## 2. حالة المشروع الحالية (مهم جداً — اقرأ قبل أي تعديل)

**ما هو موجود وجاهز:**
- واجهة أمامية كاملة الوظائف (HTML/CSS/JS بدون أي إطار عمل) في `frontend/collection-system.html`، تغطي: تسجيل الدخول، لوحة المدير، متابعة العملاء، ملف العميل التفصيلي، مركز التنبيهات (6 أنواع)، استيراد أرصدة من Excel، الأداء والحوافز، إدارة المستخدمين والصلاحيات الدقيقة، سجل تدقيق (Activity Log).
- كل منطق العمل (حساب تاريخ الاستحقاق الجديد، الأيام المتبقية، تحويل العملات لليمني، توليد التنبيهات، حساب الحافز) مكتوب كدوال JS صافية (pure functions) في أعلى ملف `<script>` — سهلة الاختبار والنقل.
- مخطط قاعدة بيانات PostgreSQL/Supabase كامل في `database/`، مصمم ليطابق حرفياً كل بنية بيانات وقاعدة عمل موجودة بالواجهة، بما فيه سياسات RLS تطبّق نفس منطق الصلاحيات.

**ما هو غير حقيقي / يجب استبداله قبل أي استخدام فعلي:**
1. **لا يوجد اتصال حقيقي بقاعدة بيانات.** الواجهة تحفظ كل شيء بمتصفح المستخدم فقط (localStorage عبر شيم مضاف، أو `window.storage` إذا كانت تعمل داخل Claude.ai). لا مشاركة بيانات بين مستخدمين أو أجهزة. **هذا أهم فجوة يجب سدّها.**
2. **تسجيل الدخول وهمي.** كلمات المرور نص صريح (`ayman123`...) مقارنة مباشرة بالكود. يجب استبدالها بـ Supabase Auth (`supabase.auth.signInWithPassword`) — البنية جاهزة بـ `database/01_link_auth.sql`.
3. **شاشة "الحوافز" غير مكتملة فعلياً.** تعرض جدولين (مستحق/مصروف) لكن لا توجد أي شاشة لإنشاء سجل حافز فعلي — المصفوفتان `incentives` و `incentivePayments` تبدآن فارغتين دائماً بالنموذج الأولي. **قرار عمل معلّق يجب حسمه** (انظر القسم 6).
4. **الاستيراد من Excel** يفترض بنية صف ثابتة جداً (يبدأ اليمني من أعلى الملف، الدولار من الصف 651، السعودي من الصف 1041) مأخوذة من ملف عميل حقيقي واحد فقط. هذا **هش** إن تغيّر شكل ملفات العميل مستقبلاً — يستحق مراجعة لجعله أكثر مرونة (اكتشاف تلقائي لعدد الصفوف بدل الاعتماد الكلي على ترتيب الأقسام فقط، أو رفع الاعتماد على "رقم صف" وترك الاعتماد فقط على اكتشاف صف العناوين كما هو مطبّق فعلاً في `findSectionHeaderRows` — تحقق أن هذا يكفي مستقبلاً).

## 3. هيكل الملفات المرفقة

```
frontend/collection-system.html   الواجهة الكاملة (تعمل مستقلة بأي متصفح فوراً، تخزين محلي فقط)
database/00_schema.sql            كل الجداول + دوال منطق العمل + Views مساعدة
database/01_link_auth.sql         ربط auth.users بـ public.users + دوال صلاحيات مساعدة
database/02_rls_policies.sql      سياسات RLS تطابق منطق الصلاحيات بالواجهة
database/03_seed_data.sql         بيانات تجريبية (فئات + عملاء) + خطوات إنشاء مستخدمين تجريبيين
AGENT_INSTRUCTIONS.md             قواعد تشغيلية لأي وكيل AI يكمل تطوير الكود
```

شغّل ملفات `database/` بالترتيب الرقمي بالضبط (00 → 01 → 02 → 03) على مشروع Supabase جديد.

## 5. قواعد العمل (Business Rules) — يجب ألا تتغيّر دون قرار واعٍ

- **تاريخ الاستحقاق الجديد** = `due_date + (grace_1+grace_2+grace_3)` يوم.
- **الأيام المتبقية** = `new_due_date - اليوم` (سالب = متأخر).
- **إجمالي المستحق بالريال** = `usd*سعر_صرف_الدولار + sar*سعر_صرف_السعودي + yer`.
- **مبلغ الحافز** = `المبلغ_المحصَّل * نسبة_الحافز / 100`.
- **تنبيهات تلقائية (6 أنواع)** تُولَّد يدوياً بزر "توليد تنبيهات اليوم" (وليست عبر Cron حالياً — يستحق تحويلها لمهمة مجدولة بالإنتاج):
  1. *قبل الاستحقاق بـ 3 أيام* — الأيام المتبقية = 3 بالضبط.
  2. *يوم الاستحقاق* — الأيام المتبقية = 0.
  3. *يسوق الآن* — إذا `status_customer = "يسوق الآن"`.
  4. *وعد بالسداد اليوم* — يوجد متابعة `next_followup_date = اليوم` ونتيجة التواصل تحتوي كلمة "وعد".
  5. *لم تتم متابعته منذ مدة* — لا توجد متابعة خلال آخر `no_followup_days_limit` يوماً (افتراضي 14).
  6. *يحتاج مراجعة المدير* — يدوي فقط، يرفعه مسؤول التحصيل من تفاصيل العميل.
  - كل تنبيه فريد لكل (عميل + نوع + تاريخ) — لا تكرار لنفس اليوم.
- **نموذج الصلاحيات (مهم جداً وفريد بهذا النظام):** فوق الأدوار الأربعة، كل مستخدم لديه تخصيص إضافي:
  - `allowed_screens`: أي شاشات يفتحها.
  - `allowed_category_ids`: أي فئات عملاء يراها (فارغة = كل الفئات).
  - `screen_permissions[screen].actions`: صلاحيات إجراء دقيقة (إضافة/تعديل/إيقاف) لكل شاشة، تتجاوز افتراضي الدور إن حُدِّدت صراحة.
  - `screen_permissions[screen].hidden_fields`: أعمدة تُخفى تحديداً عن هذا المستخدم بجدول شاشة معيّنة.
  - مسؤول التحصيل يرى العميل فقط لو: (معيَّن عليه) **و** (فئته ضمن فئاته المسموحة أو لا قيد فئة).

## 6. قرارات عمل معلّقة — يجب حسمها مع صاحب المشروع قبل البرمجة

1. **آلية إنشاء سجل الحافز:** هل يُنشأ تلقائياً عند تسجيل "تحصيل فعلي" (لا يوجد حقل "مبلغ محصَّل فعلياً" حالياً، فقط `expected_collection_amount` بالمتابعة وهو *متوقع* لا *فعلي*)؟ أم يُدخله المحاسب يدوياً بعد التحقق من السداد؟ هذا يحدد هل نحتاج جدول "دفعات محصَّلة" (Collections/Payments) جديد لم يُصمَّم بعد.
2. **جدولة توليد التنبيهات:** حالياً زر يدوي. هل يُحوَّل لمهمة مجدولة يومية (Supabase Cron / pg_cron)؟
3. **مرونة استيراد Excel:** هل ستتغيّر بنية ملف العميل (ترتيب الأقسام / أرقام الصفوف) مستقبلاً؟ إن كانت الإجابة نعم، يفضَّل الاعتماد فقط على اكتشاف صف العناوين (الموجود فعلاً) وعدم افتراض أي ترتيب صفوف مطلقاً بالتوثيق التوعوي للمستخدم.
4. **تعدد فروع/مكاتب:** النظام الحالي مصمم لمكتب واحد. لو تحتاج دعم عدة مكاتب/فروع مستقبلاً، تحتاج إضافة `office_id` كطبقة عزل إضافية بمعظم الجداول.

## 7. خطوات الإكمال الموصى بها (بالترتيب)

1. أنشئ مشروع Supabase جديد، شغّل ملفات `database/*.sql` بالترتيب.
2. أنشئ المستخدمين الأربعة التجريبيين حسب خطوات `03_seed_data.sql`.
3. أضف مكتبة `@supabase/supabase-js` للواجهة، واستبدل:
   - `attemptLogin()` → `supabase.auth.signInWithPassword`
   - `loadState()` / `saveState()` → استعلامات مباشرة لكل جدول (لا حاجة لحفظ "كل الحالة" ككتلة واحدة بعد الآن، كل شاشة تجلب بياناتها).
   - أي مكان يقرأ/يكتب `ST.xxx` مباشرة → استبداله باستدعاء Supabase المطابق (select/insert/update)، مع الإبقاء على نفس أسماء الحقول لتقليل التعديلات.
4. احسم القرارات المعلّقة بالقسم 6 قبل بناء شاشة الحوافز الفعلية.
5. اختبر سياسات RLS فعلياً بكل الأدوار الأربعة قبل النشر (خصوصاً مسؤول التحصيل مع قيود الفئة).
